Mainnet product documentation

Monitor the trust.
Preserve the exit.

Kelvara is a non-custodial risk-response layer for Solana DeFi. The current application operates on Mainnet for one exact Kamino Earn vault: it discovers a wallet's position, verifies critical control evidence, and prepares constrained withdrawal paths before an emergency.

Mainnet is live. Position inspection, control verification, 60-second in-app monitoring, immediate user-signed evacuation, and armed fast-close components operate against Solana Mainnet. The separate Devnet journey demonstrates an automated breach-to-evacuation sequence with simulated-value tokens.

Why Kelvara exists

Depositing into a protocol creates an ongoing dependency, not a one-time transaction. Program code can be upgraded. Privileged authorities can change. A vault can remain visible in a wallet while the assumptions under which the user deposited have changed.

Wallets and portfolio dashboards usually show balances and yield. Kelvara focuses on the control path behind the position and the user's ability to respond:

  1. DiscoverResolve the wallet's exact supported position, vault shares, program, and underlying asset.
  2. VerifyRead program and ProgramData accounts directly from Solana RPC instead of trusting a protocol status label.
  3. InterpretCompare current control state with explicit expected identities. Missing or invalid evidence fails closed.
  4. RespondSimulate and sign a narrowly constrained withdrawal, or prepare bounded durable-nonce exits in advance.

Kelvara does not make the underlying protocol safe. It reduces detection and reaction time when a monitored condition changes and withdrawal is still possible.

How monitoring works

1. Position evidence

Kelvara accepts either a public Solana address for read-only inspection or an explicitly connected Phantom, Solflare, or Backpack wallet. It selects only the supported Kamino vault and reports exact share data plus an estimated underlying USDG amount. A USDG token balance alone is not treated as a Kamino position. Positions at or below the exact 0.001 USDG discovery threshold are reported as dust.

2. Control-plane evidence

The backend fetches the configured kVault Program account, confirms its upgradeable-loader state, resolves its ProgramData account, and decodes the current upgrade authority. It compares those values with pinned expected identities.

3. Interpretation

A matching baseline means the specific monitored rule passes. An authority mismatch means upgrade control changed; it is a risk event requiring review, not proof that the protocol is compromised. Invalid account owners, malformed layouts, unexpected ProgramData relationships, unavailable data, and stale requests are not converted into a healthy result.

Important distinction. Kelvara currently monitors explicit control assumptions. It does not claim to detect every exploit, malicious transaction, oracle failure, liquidity crisis, or protocol bug.

Immediate evacuation

A connected position owner can prepare a full redemption of the detected Kamino vault shares back to USDG in the same wallet. This is a user-confirmed Mainnet action:

  1. Kelvara requests an unsigned withdrawal transaction from Kamino.
  2. The backend decompiles and validates the transaction before it reaches the wallet.
  3. Allowed programs, signer count, destination wallet, destination token account, instruction order, exact share amount, and priority-fee cap are constrained.
  4. The transaction is simulated and the expected destination, amount, and fee are shown.
  5. The wallet signs client-side. Kelvara receives no private key or seed phrase.
  6. The signed transaction is validated again, submitted once, and tracked by signature.

If confirmation is uncertain, Kelvara tells the user to inspect the existing signature. It does not blindly resubmit a withdrawal that may already have landed.

Armed fast close

Normal Solana transactions expire after their recent blockhash leaves the processing window. A durable nonce can keep a fully constructed transaction valid for later submission until that nonce is advanced.[1] Kelvara uses this primitive to preserve a specific withdrawal decision—not to obtain general wallet authority.

Arming protection currently performs the following Mainnet flow:

  1. The wallet authenticates with a one-time signed message.
  2. The wallet creates three user-controlled durable nonce accounts.
  3. Kelvara prepares three exact-share withdrawal variants with independent nonces and low, medium, and high priority-fee caps.
  4. The backend validates each variant; the wallet batch-signs the exact transactions client-side.
  5. The signed bundle is validated again and stored encrypted with AES-256-GCM, scoped to the authenticated wallet.
  6. Fast close checks the current position, reconciles prior signatures, and submits the cheapest still-valid tier first.

Each transaction is limited to the approved position, approved instruction sequence, approved programs, and the owner's destination. Advancing or reclaiming the nonce accounts revokes the unused authorizations and returns their rent to the owner.

Current automation boundary. Armed protection is operational on Mainnet, but Mainnet fast close is currently initiated by the user. The autonomous detection-to-submission sequence is demonstrated separately on Devnet.

Security model

  • No wallet-key custody. Connection, authentication, nonce setup, evacuation, arming, revocation, and reclaim signatures happen in the browser wallet.
  • Bounded authorization. An armed transaction can redeem the approved shares to the approved owner destination. It cannot sign arbitrary transactions or transfer protocol administration.
  • Independent validation. Prepared and signed transactions are decoded and checked against exact accounts, instruction order, programs, amounts, signer count, nonce authority, and fee limits.
  • Wallet-scoped access. Protection records require a short-lived session obtained through a one-time wallet-signature challenge.
  • Encrypted storage. Armed bundles are encrypted at rest using AES-256-GCM.
  • Fail-closed evidence. Missing, malformed, unexpected, or unavailable evidence is an error or unknown state—not a pass.
  • Replay control. A successful durable-nonce transaction advances its nonce. Unused variants require explicit revocation after one tier succeeds.

Program upgrades require special treatment

Solana's upgradeable loader can replace a program's executable code while preserving its program address.[2] Therefore, a transaction validated under old program semantics must not be assumed safe after arbitrary bytecode changes. Authority changes may create a review or response window; confirmed code changes require quarantine and renewed validation.

Separate Devnet proof journey

The Devnet demo is not the production network and not a substitute for the Mainnet application. It exists to make the full protection thesis independently observable without putting real value at risk.

The guided journey uses a disposable browser wallet and simulated-value sandbox USDC. It performs real Devnet transactions: fund wallet, deposit into Saturn Earn, discover the position, create a durable nonce, sign a bounded evacuation, trigger a controlled authority breach, submit the pre-signed evacuation, and verify the returned token balance and transaction fingerprints.

Limitations and operational status

  • Current production coverage is one exact Kamino Earn vault, not all Kamino positions or all Solana protocols.
  • The active Mainnet rules cover the configured deployment relationship and upgrade authority. Broader admin, oracle, liquidity, pause, and withdrawal-health signals remain future coverage unless explicitly shown in the app.
  • Successful evacuation depends on the underlying protocol and Solana network still accepting the constrained withdrawal.
  • Monitoring cannot guarantee advance warning. A harmful change and loss can occur before a poll or before a valid exit can land.
  • Authority continuity does not prove that program code, dependencies, economic assumptions, or governance are safe.
  • Displayed underlying value depends on Kamino's position and metrics APIs; control evidence comes independently from Solana RPC.
  • Kelvara is experimental software, not insurance, an audit, investment advice, or a guarantee against loss.
  • Public API contracts, broad protocol coverage, pricing, and service-level objectives have not been announced.
